Telemetry

We build it ourselves. We track only the essential signals.

1. What we track

Every service

  • Requests per second, error rate, p95 latency (per endpoint)
  • App logs with trace_id
  • CPU and memory
  • Restarts and crashes

Load balancer / gateway

  • Access logs: route, status, latency, trace_id
  • 5xx rate

Postgres

  • Up or down
  • Query latency + slow query log
  • Connections used vs max
  • Replication lag
  • Disk space

Redis

  • Up or down
  • Memory used vs max

Kafka

  • Consumer lag
  • DLQ size

3rd parties

  • Error rate and latency of each call
  • Webhooks received and failed

Business

  • Checkout success rate
  • Payment success rate
  • Orders stuck in PENDING > 15 min
  • Failed emails

Changes

  • Deploy markers on graphs

4. Tool design rules

  • Read-only first. Actions (restart, rollback) only later, with human approval.
  • Time window required. Default: last 1h.
  • Small output. Top N, counts, summaries.
  • Compare to normal. "4.1% (normal 0.2%)".
  • Remove PII in the tool, not in the prompt.
  • Return linking IDs: trace_id, order_id, service.
  • Clear errors: "No metric X. Did you mean Y?"

5. Example investigation

list_alerts            → "checkout error rate 6%" since 10:12
list_changes           → payment v2.3.1 deployed at 10:10
top_endpoints(payment) → POST /payments: 40% errors
log_patterns(payment)  → "stripe: invalid api version" ×812 (new)
get_trace(sample)      → Order → Payment → Stripe 400
stuck_orders(PENDING)  → 214 orders

Result: the 10:10 payment deploy broke the Stripe call. 214 orders affected.
Suggestion: roll back payment to v2.3.0.
